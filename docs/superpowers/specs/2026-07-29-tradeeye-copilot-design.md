## 一、产品定义

> **TradeEye Copilot 是面向买方研究员的 A 股财报披露即时研判系统。财报落地 3 分钟内，输出事实级准确的财务数据、规则驱动的异常发现与依据溯源，并给出市场反应上下文。不提供投资建议。**

对外场景标签沿用官方参考场景「智能投研助理」，降低评委理解成本；内核能力是**异常发现与优先级排序**，这是区分度所在。

### 1.1 解决的痛点

财报摘要是免费商品（Wind / Choice / 券商晨会都有），买方研究员不缺摘要。他们缺的是：

- 披露高峰期（4 月、8 月、10 月）一晚收到十几份财报，**不知道先看哪几份**
- 口径悄悄变更、财务指标间背离、管理层措辞退坡等**需要纵向对比才能发现的问题**，人工翻阅极易遗漏

系统交付的不是"总结当期数字"，而是"找出这份财报里值得追问的地方，并给出可复核的依据"。

### 1.2 明确不做

| 不做 | 原因 |
|---|---|
| 荐股 / 买卖建议 / 目标价 | 《证券投资顾问业务暂行规定》需持牌；且预测不可当场验证 |
| 短线技术信号选股 | 用户画像是研究员（季度—年持仓），非交易者；TradeEye 已有此能力，重做无增量 |
| 公告流泛异动监控（减持/担保/诉讼） | 会把主线漂成第二个产品，10 天内做不完；架构留 `Rule` 接口，答辩作为扩展方向口头回答 |
| 产业链映射树 | 手工维护的 JSON，扩展性为负，与评分表"跨场景复用价值"相悖 |
| 飞书交互卡片回调（原位刷新） | 需公网 HTTPS 回调，约占工期 1/3；属完成度而非区分度；现场演示依赖链过长 |
| 向量检索 / RAG | 措辞对比用 LLM 直读两期原文更准（相似度只能说"变了"，说不出"怎么变了"） |
| NPU 本地部署 | 规则明确允许昇腾 API；无显卡，环境调试成本不可控 |

### 1.3 产品节奏：披露驱动，非自然日历

财报阅读天然是事件型的。A 股披露集中在三个窗口，全年约 60–70 天有密集财报。系统在有披露时工作，非披露日安静——这是正确行为，不是缺陷。

三个视图对应三个真实使用时刻：

| 视图 | 使用时刻 | 内容 |
|---|---|---|
| 公司研判卡 | 财报刚落地 | 四层结构 + 依据溯源 |
| 当日汇总 | 披露高峰的晚上 | 全量披露公司，按严重度排序 |
| 披露季复盘 | 季末 | 全池分布 + 准确率 benchmark |

非披露日展示披露日历与业绩预告变动（`forecast` / `express` 接口），成本低，不额外开发主线功能。

## 二、输出形态

### 2.1 当日汇总（顶部）

```
2025-08-21 财报研判 · 覆盖池 42 只
今日披露 12 家 | 🔴 需优先关注 2 | 🟡 留意 3 | ✅ 未见异常 7
硬校验未通过 0 | 数据完整度 12/12
```

末行刻意展示校验状态：让研究员知道结论可信，让评委看到有校验层。

### 2.2 公司研判卡（四层）

| 层 | 内容 | 来源 | 幻觉风险 |
|---|---|---|---|
| ① 事实 | 营收 / 净利 / 扣非净利 + 同比环比、毛利率、净利率、经营现金流 | tushare + pandas | 零 |
| ② 异常 | 命中规则，按严重度排列，每条含具体数字与 `[依据]` 入口 | 规则引擎，纯算术 | 零 |
| ③ 归因 | 一段话解释变化来源 | LLM（昇腾 API） | 有，但不涉数字 |
| ④ 市场 | 披露后首日涨跌、成交量、主力净流入、量比 | TradeEye 行情模块 | 零 |

示例：

```
🔴 XX科技 002xxx  2025 半年报
① 营收 128.4亿 (+12.3% yoy) | 净利 15.2亿 (+8.1%) | 扣非 11.8亿 (-3.2%)
   毛利率 31.2% (-2.4pct qoq) | 经营现金流 4.1亿（净利的 27%）
② ⚠️ 应收账款 +47% vs 营收 +12%，背离 35pct  [依据]
   ⚠️ 经营现金流/净利润 = 27%，连续两期低于 50%  [依据]
   ⚠️ 净利 +8.1% 但扣非 -3.2%，非经常性损益贡献 3.4亿  [依据]
③ 归因：增长主要来自……但现金回款未同步……
④ 市场：披露次日 +6.2%，主力净流入 2.3亿，量比 3.1
   [同业对比] [看管理层原文] [导出]
```

第④层只陈述事实，不写方向性结论，判断权保留在研究员手中。

未见异常的公司折叠为一行：`ZZ集团 601xxx 营收+8.2% 净利+9.1% ✅ [展开]`。全量覆盖，但注意力加权分配。

```
                                ▼

        │              数据装配层（Context）             │
        │  本期 / 上期 / 去年同期 财务快照 + 行情窗口     │
        └───────────────────┬───────────────────────────┘
              ┌─────────────┴─────────────┐
              ▼                           ▼
     ┌─────────────────┐         ┌─────────────────┐
     │  硬校验层        │         │  原文抽取层      │
     │  交叉验算/完整性 │         │  PyMuPDF 抽段落  │
     └────────┬────────┘         └────────┬────────┘

     │ ★ 异常规则引擎       │     │  语气对比（LLM）     │
     │   背离 / 口径        │     │  昇腾 API            │
     │   纯算术，零 LLM     │     └──────────┬──────────┘
     └──────────┬──────────┘                │
                └────────────┬───────────────┘
                             ▼
              ┌──────────────────────────────┐
              │  研判编排器                   │
              │  全量渲染 + 严重度排序 + 标注 │
              │  归因摘要（LLM，昇腾 API）    │
              └──────────────┬───────────────┘
                ┌────────────┴────────────┐
                ▼                         ▼
        ┌───────────────┐         ┌───────────────┐
        │  Web 看板      │         │  飞书 webhook │
        │  溯源/展开/对比│         │  静态推送提醒 │
        └───────────────┘         └───────────────┘
```

**核心原则：LLM 永不接触算术。** 所有数字来自 tushare + pandas，LLM 仅负责语气判断与文字摘要。这使"事实级准确"可验证，也让 LLM 故障不影响主链路。

### 3.2 规则引擎接口

对应评分表「系统可扩展性与跨场景复用价值 10 分」——引擎不认识金融，规则是插件。

```python
@dataclass
class Evidence:
    source: str        # "tushare.balancesheet" | "pdf.p47"
    field: str         # "accounts_receiv"
    period: str        # "20250630"
    value: float | str

@dataclass
class Finding:
    rule_id: str
    severity: Severity      # RED / YELLOW / INFO
    title: str
    detail: str             # 含具体数字
    evidence: list[Evidence]
    score: float            # 排序权重

class Rule(Protocol):
    id: str
    def applies(self, ctx: Context) -> bool: ...
    def evaluate(self, ctx: Context) -> Finding | None: ...
```

答辩表述："引擎只依赖 `Context` 与 `Rule` 两个抽象。迁移到风控场景，替换一套 `Rule` 实现与一个 `Context` 装配器，编排、排序、溯源、看板全部不动。"

`Evidence` 是溯源载体：规则计算时顺手记录数据来源、字段、报告期、原始值。看板上每个数字可点开查看，直接对应可解释性要求。

## 四、规则集

分三批，优先级按"判断标准客观、单人可复核"排序。

### 第一批：背离类（纯算术，必做）

| 规则 | 判据 |
|---|---|
| 应收账款增速背离 | 应收账款 yoy − 营收 yoy > 阈值 |
| 存货增速背离 | 存货 yoy − 营收 yoy > 阈值 |
| 现金流质量 | 经营活动现金流净额 / 净利润 < 阈值，连续两期 |
| 毛利率异动 | 毛利率环比变动绝对值 > 阈值 |
| 利润与营收方向背离 | 净利 yoy 与营收 yoy 符号相反 |

### 第二批：口径类（算术，需理解财务含义）

| 规则 | 判据 | 精度说明 |
|---|---|---|
| 非经常性损益占比 | (净利润 − 扣非净利润) / 净利润，及其同比变动 | 精确。`fina_indicator.profit_dedt` 直接提供扣非净利润 |

原候选规则「研发费用资本化率变动」已剔除：tushare 无直接字段，只能由 `balancesheet.r_and_d`（开发支出）期间变动估算，精确数据在财报附注中。输出估算值会削弱"每条结论可复核"这一核心主张，故不纳入。

### 第三批：措辞类（LLM 判断，仅覆盖有原文缓存的公司）

| 规则 | 实现 |
|---|---|
| 管理层展望语气退坡 | 抽取两期"管理层讨论与分析/未来展望"章节，一并交由 LLM 判断语气是否转弱并指出具体措辞变化 |

共 7 条规则（背离 5 + 口径 1 + 措辞 1）。阈值全部写在配置文件中，文档标注可配置。规则本身是算术，答辩时解释的是财务常识而非主观判断。

## 五、数据链路

数字规则全部走 tushare 结构化接口，不解析财报表格。

| 接口 | 用途 |
|---|---|
| `income` | 营收、营业成本、研发费用、净利润 |
| `balancesheet` | 应收账款、存货、开发支出 |
| `cashflow` | 经营活动现金流净额 |
| `fina_indicator` | 毛利率、ROE、扣非净利润 |
| `disclosure_date` | 披露计划 → 事件触发 |
| `forecast` / `express` | 业绩预告、快报（填非披露期） |

**tushare 拿不到**：管理层讨论与分析原文、附注文本、风险因素章节 → 措辞层走 PDF（PyMuPDF），仅预处理演示用的 3–5 家公司。文档诚实标注措辞比对为试点能力，非全池覆盖。

覆盖池规模按研究员真实工作方式设定（30–50 只）。评委问及扩展性，回答："解析器与规则通用，入池即可，无需预热 5000 家。"

## 六、时序与降级

```
T+0     披露日历轮询命中（或手动触发单只）
T+5s    装配 Context：三期财务快照 + 行情窗口（披露日前后 5 日）
T+10s   硬校验：不通过 → 标记 DATA_INCOMPLETE
T+15s   规则引擎全量执行（纯 pandas，毫秒级）
T+20s   PDF 抽取管理层展望（仅当有上期原文缓存）
T+60s   LLM：①语气对比 ②归因摘要（昇腾 API）
T+90s   落库 findings + 渲染研判卡
T+2min  当日汇总重算排序 → 飞书 webhook 推送
```

对外报"3 分钟内"，留余量。**规则引擎在 LLM 之前完成且不依赖它。**

### 6.1 失败行为

| 失败点 | 行为 | 用户可见 |
|---|---|---|
| tushare 限流/超时 | 指数退避重试 3 次，仍失败入待重试队列 | 汇总页"N 家待重试" |
| tushare 字段缺失（如新股无去年同期） | 相关规则 `applies()` 返回 False | 研判卡注明"因缺少去年同期数据，N 条规则未执行" |
| 硬校验不通过 | **不出研判卡**，仅报警 | 汇总页"⚠️ 数据校验未通过，已挂起" |
| PDF 无上期原文 | 措辞层跳过 | "未启用措辞比对（缺上期原文）" |
| LLM 超时/报错 | 研判卡照出，③层占位 | "归因生成失败，可重试" |

"硬校验不通过就不出卡"是刻意的严格设计：宁可少报，不报错数字。答辩时主动讲。

LLM 故障不阻断主链路 → 保障现场演示稳定性。

## 七、昇腾接入

规则 2.3 为硬性准入：作品必须运行在昇腾算力底座（NPU 或昇腾 API 均可）。本项目走 **API 路线**。

**接入路径（按优先级）**：
1. 华为云 ModelArts Studio（MaaS）——昇腾适配版模型，OpenAI 兼容 `/v1/chat/completions`，有免费 Tokens
2. 华为开发者空间百万 Tokens 活动
3. 昇腾 NPU 实例（不走，无显卡）

技术成本：`llm_client.py` 是单出口设计，改 `base_url` / `model` / `api_key` 三项 + 异常适配，约 1–2 小时。注意仅换 `api_key` 不换 `base_url` 无效——请求仍会发往原端点。

### 7.1 配置与密钥分离

Plato 现状把端点与密钥都放在 `config.yaml`，存在误提交风险。本项目拆分：

```
.env（进 .gitignore，不入仓库）
  ASCEND_API_KEY=...
  TUSHARE_TOKEN=...
  FEISHU_WEBHOOK=...

config.yaml（入仓库）
  llm:
    base_url: <昇腾 MaaS 端点>
    model: <模型名>
    timeout: 60
  rules:
    thresholds: {...}
```

密钥走环境变量，端点/模型名/阈值走配置文件。`.env.example` 入仓库充当配置文档，评委 clone 后即知需配置哪些项（对应"文档规范度"）。`llm_client` 从 `os.environ` 读取密钥，不落盘、不打印。

**必须分清**：赛事 2.4 节发放的 AtomCode CodingPlan（deepseek-v4-flash / GLM-5.2 / Qwen3）是**开发期 IDE 助手额度**，与 2.3 节要求的"作品运行时推理端点跑在昇腾上"是两件事。领取 AtomCode 不等于满足 2.3。

**风险处置**：端点可用性须在 D1 验证（发一个测试请求），不得拖到 D5。

**深度补强（零额外成本）**：D8 批量评估需跑一整个披露季，每家公司调用昇腾完成归因与语气判断。顺手记录延迟与 token，产出真实性能表：

```
昇腾 API 推理统计（2025 半年报季批量评估）
调用次数 76（38 家 × 2 类任务）  平均延迟 8.2s / P95 14.1s
总 token 约 21 万   全季批量耗时 11min
```

**退化方案**：若端点确实拿不到，因 `llm_client` 单出口 + LLM 不在关键路径 + 仅两处调用，切换任意 OpenAI 兼容端点改一行配置，功能不损失。但会丢失技术创新性相关得分，并存在初审合规风险，故仅作心理保险，不作为计划路径。

## 八、测试与自证

### 8.1 规则单元测试

规则是纯函数（`Context → Finding | None`），无 IO。每条规则 3 个用例：应触发 / 不应触发 / 边界值。采用 TDD。

### 8.2 黄金样本回归

5 家公司真实财报，人工确认每条 finding 真伪，固化为 fixture。改阈值时立即发现回归。

### 8.3 批量评估（README benchmark 来源）

`eval/run_backtest.py` 跑覆盖池最近一个披露季，人工复核全部命中，输出：

```
2025 半年报季 · 覆盖池 42 家 · 已披露 38 家
命中 27 条 → 人工复核 24 条为真
精确率 88.9%   假阳性 3 条
分布：背离 13 · 口径 6 · 措辞 5 · 现金流 3
端到端耗时 P50 1.8min / P95 2.9min
```

同一份数据三处使用：README benchmark、路演 PPT 一页、季度复盘视图。人工复核约 20–30 条，单人可完成。

**注意**：官方 2.2 节的「简报 < 30min / 准确率 > 95% / 使用率 > 70%」是参考场景指标，不在第 4 节评分表内。作为落地性证据引用，不作为设计目标反推功能。其中"使用率"无真实用户无法测量，改用可测替代指标（端到端耗时、零输入操作占比）。

|---|---|
| TradeEye | tushare 行情特征工程（MA/量比/资金流/全市场 rank）、RSS 抓取器（纯 `xml.etree`，无第三方依赖）、飞书 webhook（`msg_type: text`）、51 个通过测试 |
| platoacademy | `llm_client.py` 单出口 LLM provider 层、`parser.py` PDF 三层降级链（MinerU → PyMuPDF → 视觉模型）、SQLite 13 表、前后端低耦合结构（REST + 静态页） |

### 原企划书判断有误之处

| 企划书称 | 实际 |
|---|---|
| Plato 有"无头 Skill Agent 编排" | 无编排、无 agent loop。是 FastAPI → service → 单次 `llm_client.chat()`。`skills/` 三个 md 自述为占位 |
| Plato 有"RAG 检索" | 无向量库、无 embedding、无 rerank。检索为 SQLite 直查 + 原文塞 prompt |
| TradeEye 有"飞书推送机制"（含卡片） | 仅 webhook 发纯文本。无 app_id/app_secret、无 tenant_access_token、无交互卡片、无 callback |
| TradeEye 有财报解析 | 无。无 BeautifulSoup/pdfplumber/PyMuPDF，无公告接口 |

### 其他

- 两仓库均无任何昇腾 / CANN / MindSpore / NPU 痕迹，需从零对接
- TradeEye 与 platoacademy 的 LLM 调用是两套实现（requests / httpx），统一到 `llm_client`
- platoacademy 的 `.venv` 已提交在目录内，迁移时勿整体复制
- `parser.py` 的 MinerU 与视觉层均为外部付费服务；本项目只用 PyMuPDF 本地层
- tushare pro token 已具备且积分充足
